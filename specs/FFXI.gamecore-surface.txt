FFXI -> gamecore surface: what FFXi.dll / FFXiMain.dll use, and gamecore as a recompile target
=================================================================================================
Date: 2026-09-24. Static only (no run). Ghidra MCP was not reachable (connection refused on :8080);
everything below is capstone 5 + pefile over the unpacked images in reverse-engineering/unpacked/,
image base 0x10000000, plus FFXiMain.2026-08-22.meta.json for FFXiMain's function list.
Scratch scripts (not in repo): session scratchpad {img,cfg,thunks,uses,funcs2,slots2,group,appscan,gref}.py

---------------------------------------------------------------------------------------------------
0. THE HEADLINE CORRECTION TO client-gamecore-interface.md s4/s6
---------------------------------------------------------------------------------------------------
* Both FFXi.dll and FFXiMain.dll statically link the SAME gamecore stub library: 672 thunks of the
  form   A1 <tbl>  FF A0 <disp32>   = mov eax,[tbl] ; jmp [eax+disp]   covering +0x1f8..+0x1800.
  The doc's byte scanner looked for `call [r+disp]`, so it missed them (they are JMPs).
    FFXi.dll     thunks 0x100057a0..0x1000747a, table ptr global 0x10018b40
    FFXiMain.dll thunks at 0x1030ff10.. (e.g. slot +0x30c = 0x103100a7), table ptr 0x10456a6c
    app.dll      24 thunks (global 0x105c7c84), TM.dll 4 thunks (0x1024dfe8)
  All 672 thunks are linked whether used or not, so the thunk list is NOT the usage list. Usage =
  direct call/jmp sites to thunks (below).
* FFXiMain DOES call the common function table directly. It gets the pointer through the param
  block: FFXi.dll puts it at block+0x0C; FFXiGameMain (0x100157e0) copies it:
      100157e9 mov eax,[0x104569f4]      ; block+0x0C
      1001580f mov [0x10456a6c],eax      ; = block+0x84, the thunks' table global
  0x1001580f is the only non-thunk reference to 0x10456a6c.
* FFXiMain never uses the ICoreCom object. The FFXiGameMain wrapper 0x100157b0 forwards
  (pCore,pFFXi) to 0x100157e0, which passes them on to the main loop 0x10015ab0. That loop ends
  `ret 8` and never reads either argument (checked: neither range reads them via [esp+x]). So
  FFXiMain's whole gamecore dependency is the table.
* For FFXI, input does NOT come from gamecore: FFXi.dll never calls CreateInput/UpdateInputState/
  GetPad*, and FFXiMain imports DINPUT8 itself.

---------------------------------------------------------------------------------------------------
1. FFXi.dll <-> ICoreCom                                        confidence: HIGH (read directly)
---------------------------------------------------------------------------------------------------
GameStart body is 0x100047d0 (sub esp,0xa20). Sequence:
  - CoInitialize; CreateMutexA (single instance); if the mutex already exists -> table slot +0x1008
    (error message, 0x1000498d) and exit.
  - Region probe, in this order. Each step does QI(pCore, IID) then 3 methods, and the probe stops
    at the first success:
      0x10005310  IID {9A30D565-A74C-4B56-B971-DCF02185B10D}  -> region index 0  (JP, presumably)
      0x100053e0  IID {E0516654-EF77-435D-AA7D-50D2C069CE34}  -> region index 1  (US, ICoreCom)
      0x10005240  IID {DFEC2E93-4971-4A54-B8ED-63815C208C5A}  -> region index 2  (EU, presumably)
    Methods called in each (US copy, 0x100053e0):
      vtbl+0x00 QueryInterface
      vtbl+0x10 GetlpCmdLine(&g_cmdline 0x10018ad8)          (slot 4)
      vtbl+0x0C GethInstance(&g_hinst 0x10018ad4)            (slot 3)
      vtbl+0x1C GetCommonFunctionTable(&0x10018b40)          (slot 7)  -> copied to 0x10018adc
      vtbl+0x08 Release
  - After the game returns, the same three IIDs are tried again (0x10005390 / 0x10005460 / 0x100052c0):
      QI, vtbl+0x20 ViewerExec(g 0x10018af4 = the value FFXiMain left in block+0x24), Release.
  - That is all the COM FFXi.dll uses: QI, Release, GethInstance, GetlpCmdLine,
    GetCommonFunctionTable, ViewerExec. It never calls SetParamInit, AreaCode, the mask window,
    the friend list or input.
  - Table slots FFXi.dll itself calls (6 distinct, 6 sites):
      +0x0694 (421) 0x10004790  region/language code (gamecore 0x10018200 returns a global) -> block+0x28
      +0x0730 (460) 0x10004a4e  returns global 0x1009aa58 (a flag) -> block+0x44
      +0x0f54 (981) 0x10004dfb  "-patch" path: returns 0x10000 (a size)
      +0x0f58 (982) 0x10004e09  "-patch" path: fills buffer (0x1003963a)
      +0x0f24 (969) 0x10004fff  at exit with 0 / -14 / -15  (stores an error code, gamecore 0x1004a440)
      +0x1008 (1026) 0x1000498d error path: (code, message) -> copies msg into gamecore 0x103dfd28
Param block (FFXiMain 0x104569e8, 0x58 bytes). FFXi.dll gets it through IGameMain vtbl+0x10
(FFXiParaGet) at 0x10004e6e. It fills the block with `rep movsd` of 0x16 dwords from its own
0x10018ad0 (0x10004e7f):
  +0x00  (overwritten by FFXiMain with its HWND at 0x1001590c)
  +0x04  hInstance              <- ICoreCom::GethInstance
  +0x08  lpCmdLine              <- ICoreCom::GetlpCmdLine        (FFXiMain passes to 0x10001e00)
  +0x0C  COMMON FUNCTION TABLE  <- ICoreCom::GetCommonFunctionTable  (FFXiMain -> 0x10456a6c)
  +0x10  current directory string (GetCurrentDirectoryA)
  +0x14/+0x18 build date/time strings "Aug  5 2026" / "10:54:39"
  +0x1C..+0x1E  byte flags read back after the game (restart / exit variants)
  +0x20/+0x24  read back after the game; +0x24 is handed to ViewerExec
  +0x28  region/language code (table slot 421)       +0x2C region index 0/1/2 (which IID matched)
  +0x30/+0x34 pointers to two random a-z strings (9-11 and 7-9 chars) generated at start
  +0x44  byte from table slot 460                   +0x48/+0x4C init 0/1
  +0x50/+0x54 read back (0x10018b20/b24) - "next step" loop control
The ICoreCom pointer itself is NOT put into the block; the table pointer is.

2. Table slots called                                    confidence: HIGH for sites found, see limits
---------------------------------------------------------------------------------------------------
Method: find the thunk addresses by byte pattern. All 672 in a module use one global, so there are
no false positives. Then collect every call/jmp rel32 to a thunk, and every immediate equal to a
thunk address (none were found: no thunk is ever taken by address). FFXiMain was scanned by
disassembling every function range in FFXiMain.2026-08-22.meta.json (996,120 insns); FFXi.dll by a
linear sweep. Also listed every other reference to the table global: only the 0x1001580f store in
FFXiMain, and three stores in FFXi.dll.
   FFXi.dll     :   6 distinct slots,   6 call sites
   FFXiMain.dll : 141 distinct slots, 327 call sites (incl. 30 tail-jmps from 1-line wrappers)
   union        : 144 distinct slots (421, 969, 1026 used by both)
   of which app.dll (Viewer) also calls 64; 80 are FFXI-only.
   app.dll for comparison (same method + global-load tracking): 425 distinct slots, 2,227 sites.
Limits: a slot reached only from code missing from the meta function list, or only through a
function pointer built at run time, would be missed. No immediate references to thunks exist, so
the second case is unlikely. A slot called from inside an indirectly-called FFXiMain function is
still counted, because the call to its thunk is itself direct.
Full per-slot list with call sites and gamecore behaviour: section 7.

3. What gamecore does behind each used slot                         confidence: MEDIUM (heuristic)
---------------------------------------------------------------------------------------------------
Method: slot -> u32(0x1006fbe8+disp) -> recursive descent in gamecore, following direct calls only.
The descent stops at the statically linked library (ATL + VS2005 CRT, from ~0x1004f4e0): library
functions are recorded as "lib" and not descended into, except 1-2 insn import stubs. Imports and
strings reached are collected. Indirect calls (C++ vtables, callbacks) are NOT followed, so reach
is a lower bound.
Groups (144 slots):
   A trivial (<=40 insns, no OS call: getters/setters/copies/constants)     27 (+2 GetTickCount-only)
   B internal (gamecore state, lists, buffers, parsers, sprintf-like; sync only) 86
   B os-wrap  (thread/registry/DNS etc., no sockets)                        13
   C network  (reach WS2_32 via gamecore's sqsocket/presence engine)        16
Union of reach: 516 gamecore functions, ~28.5k instructions out of ~126k, so ~20% of gamecore.
Without the 16 network slots it is ~330 functions / 15.8k insns.
Recognisable clusters (strings in the FFXiMain caller or the gamecore callee):
  - Paths/files: 126 (install path by id: (0x14,buf,0x200), "Contents%04d"), 127 (file-name table:
    sqpoliop.bin, sqpolkey.bin, sqpolexe.bin, fnt%03d.bin, vulgar2.dic/vulgaru.dic), 284-287, 908,
    910, 1135, 1296 ("Contents%04d"), 477 ("download\", "cicn_l"), 1171 (registry
    HKLM Interface key of the launcher (US/non-US variants, see gamecore-slots.files.txt), stored
    Caesar-shifted +1 in the binary); FFXiMain uses 1171 with "patch.ver".
  - libc-like helpers: 258 (sprintf-like, 0x10012420), 293/297/299 etc.
  - presence client (profile/files/lists/mail, "u/s/select%d", "O/m/", "U/g/0001_00.bak"):
    the 165-209 and 270-302 blocks, 463-465 (FFXiMain "netwait"/"FFXI%d.DAT"), 1483
    (the service's mail header lines), 1071 (msgline).
  - Knowledge-base/FAQ search: 422, 638-669 (kb_faq.pib, "KBSearch", z_id/z_ans).
  - Profanity filter: 362/363, 1109/1110 (vulgar2.dic, entryz.dic).
  - Lobby session: 195/196, 221/222, 936, 1003, 818 (section 4).
  - Per-frame session pump: 705 (FFXiMain 0x100daf40, every frame) and 818. Both call gamecore
    0x10045480, which returns 1 if the online session is not initialised and otherwise runs the
    session engine.
None of the 144 reaches DINPUT8, GDI or the mask window.

4. Session dependency                                               confidence: HIGH on the path,
                                                                    MEDIUM on slot 936's meaning
---------------------------------------------------------------------------------------------------
FFXiMain has its own sockets: it imports 32 WS2_32 functions and runs the lobby and zone
connections itself (TCP client thread 0x100d8530, created by 0x100d84a0; UDP 0x100dc440). No lobby
or zone port is a constant in FFXiMain (searched 54001/54230/54231/51220 in both byte orders:
none).
The lobby bring-up is the state machine at FFXiMain 0x100ed7f0 (lobby host name string):
  step 0  slot 818 (+0xcc8)  online-session pump must return 0 or 1
  step    slot 221 (+0x374)(lobby host) -> async resolve handle (gamecore 0x1000ff40, own thread)
  step    slot 222 (+0x378)(h,&hostent-ish) -> IPv4 bytes -> inet_ntoa -> lobby address
          (the port comes from FFXiMain's own state [0x104df7b0]+0x10, htons'd)
  step    slot 195 (+0x30c)(-2,-1,0,-2,-1,1) -> handle; slot 196 (+0x310)(h) polled: 0 wait, >0 done
          gamecore 0x1001db60 -> 0x1001db90 is a presence-service connection state machine:
            resolve the numbered presence host (fmt 0x10075430), connect port word 0xC814 (the
            project's live notes identify this as presence port 51220; the raw store is
            `mov word [esi+0x26],0xC814`),
            send request cmd 4 sub 5 len 0x28 (0x1001f4d0(conn,4,5,0x28)). The request header
            carries an MD5 over globals 0x10404a88/0x10404a8c (8 bytes) + 0x10404a94 (15-byte
            string) + a per-connection dword (0x1001f5e0).
            On reply: first 0x10 bytes of the body -> 0x100aaad0 (1001ddaa);
                      0x1001a2d0(0x104057b0, ...) derives a 0x34-byte block (1,550 insns, pure
                      computation, no imports).
  step    slot 936 (+0xea0)(buf) copies the 0x34-byte block 0x104057b0 -> FFXiMain 0x101163d0 ->
          lobby object +0xa24 (+0xa20=1). It is later copied into outgoing lobby packets
          (0x10116620, 0x101167f0) and used by 0x10116d90/0x100d7ee0.  Best guess: the authCode
          block.
  step    slot 1003 (+0xfac)(buf) copies the 16 bytes at 0x100aaad0 -> FFXiMain 0x101164e0 ->
          lobby object +0x10: this is the SESSION VALUE V of the LSB integration notes s3.
This static read CONFIRMS the doc's Phase-0 hypothesis from the client side. FFXI's session value is
the first 16 bytes of the reply to presence cmd 4 sub 5; gamecore fetches it at FFXiMain's request and
hands it over through slot 1003.
The one input that exists only after an online-session sign-in is the credentials that
authenticate that presence request (0x10404a88/8c, 0x10404a94). Only 0x1001e9b0 / 0x1001eab0 /
0x1001ea60 write them, and those are reached only from the sign-in state machine 0x10044a50 (= slot +0xcbc) and
from init with NULLs. No table slot sets them directly. The presence/sqIrc accessor clusters above
(friend list, the service's mail, profile files, KB search) also depend on the session; the host can treat
them as optional.
Where the lobby address comes from: gamecore resolves the lobby host name by DNS (221/222); no account
server supplies it. The port is FFXiMain-internal.

5. gamecore as a recompile target                                 confidence: MEDIUM-HIGH
---------------------------------------------------------------------------------------------------
Size: .text 0x63bc1 = 408,513 bytes (FFXiMain 3,307,520 -> 12%). .data vsize 3.6 MB (mostly bss).
Functions: ~2,657 by recursive descent, covering 381 KB = 93.4% of .text, ~126k insns. Seeds: the
entry point, the exports, every .data/.rdata pointer into .text, then every push/mov immediate
into .text, iterated to a fixed point.
  own code ~2,018 functions (<0x1004f4e0, ~99k insns); ATL + CRT ~639 (upper bound, some noise).
  FFXiMain: 21,873 functions / 996k insns -> gamecore is ~1/8.
Toolchain: linker 8.0 (VS2005), built 2011-08-19, /GS security cookie (__security_check_cookie at
0x100503d8), VS2005 CRT (FLS/TLS via GetProcAddress, _resetstkoflw, SSE2 memcpy path).
FFXiMain/FFXi are linker 6.0 (VC6). So the recompiler's CRT-surface and SEH handling, built for
VC6, would need a second profile: VS2005 _except_handler4 (cookie-encoded scope tables) and
different CRT entry points. This is the single biggest unknown for option (b).
No packing or self-checks beyond the packed .text section were found. IsDebuggerPresent appears only in the CRT
(0x100503d8, 0x1005757b), and VirtualProtect only in the CRT (0x100526d1 _resetstkoflw). NOTE:
.reloc has no entries for .text at all (all 2,286 HIGHLOW fixups are in .data/.rdata), so the
.text fixups must live in the packer stub's own data. This does not matter if the image is loaded
at 0x10000000, as the recompiler assumes.
Imports (10 DLLs, 200 functions): KERNEL32 127, WS2_32 31, ADVAPI32 10 (registry +
GetCurrentHwProfileA), OLEAUT32 8, USER32 6 (incl. SetWindowsHookExA), GDI32 6 (BitBlt family:
friend-list painting), ole32 6 (CoCreateGuid, CoCreateInstance), IMM32 4, DINPUT8 1, WINMM 1.
No crypto API: MD5 (0x10018830/860/910) and the ciphers are in-house code.
Threads: 5 CreateThread call sites (0x100129fb generic wrapper, 0x1003c840 sqsocket worker,
0x1004187e proc 0x10041b53, 0x1004b6e6 wrapper, 0x10054176 CRT _beginthreadex). The run-time thread
count is not fixed statically, because the wrappers take the thread proc as an argument.
SIMD: none in own code; 24 movdqa + 1 pxor, all in CRT. x87: 111 insns (91 own).
C++: 31 RTTI type descriptors, 6 C++ EH FuncInfo (0x19930520); 5 fs:[0] frame sites.
Indirect call/jmp sites: 466 (329 own code) + switch tables (resolved).
COM: ATL CComObject<CCoreCom>, creator 0x100067fd; uses LoadRegTypeLib/RegisterTypeLib. A
recompiled gamecore would be instantiated by calling the creator directly, not through the registry.
Registry: gamecore reads the launcher's registry keys at init and in slot 1171, so a host must emulate them.

6. What a native host still has to do if gamecore is recompiled         confidence: MEDIUM
---------------------------------------------------------------------------------------------------
app.dll's GameStart (per doc s5) makes only COM calls; the Viewer's sign-in runs through the table:
  - +0xcbc (gamecore 0x10044a50) is the sign-in state machine. It has 42 states (jump table
    0x10045224) and takes no arguments. app.dll polls it at 0x1019ce64, from a UI handler that
    switches on its return code.
    Direct reach: 172 functions, ~9.1k insns, sockets, CreateThread, CoCreateGuid, strings
    the presence host format, "sqsocket%08x", "pQ9CXz56K2J6yDL", Iphlpapi GetIfTable/GetTcpStatistics.
    It is the only path that installs the presence credentials FFXI's lobby needs (s4).
  - Its inputs come from gamecore's member store (0x10099280.., filled at init by
    0x10046e70/0x10046ee0/0x10047390 and decoded by 0x10046f80) and from other slots the Viewer
    calls. A global-overlap heuristic finds 65 slots that write globals this machine reads, and 42
    of them are called by app.dll. That is an UPPER BOUND on the sign-in input surface; the true
    set is not determined.
  - Hand-off to the game: nothing at slot level. Viewer and game run in the same process on the
    same gamecore object, so the state simply carries into FFXi.dll's GameStart. app.dll's
    GetNextApplication tells the retail launcher what to launch.
So with a recompiled gamecore the host must do one of two things:
   (b1) drive +0xcbc and its input slots against the account server (sqIrc 51240 + presence 51220). That
        means reimplementing the Viewer's sign-in UI flow, which is not mapped yet.
   (b2) call gamecore's internal 0x1001ea60(id_string, str15), or write 0x10404a88/8c/94 (and
        optionally the sockaddr override 0x10404ab8) directly. Both are trivial in recompiled C.
        the account server's presence service must still run, so that cmd 4 sub 5 gets an answer. Not read yet:
        what 0x10404a94 must contain (password? nick?), and how 0x10019f20/0x1001a020 map the ID
        string to 64 bits.
Compared with implementing FFXI's slots natively: (b1) is more work. (b2) is less than the full
144 slots, but it still needs a presence server reachable from the Mac and a working recompile of a
VS2005 binary.

ESTIMATE: which is faster                                             confidence: MEDIUM
---------------------------------------------------------------------------------------------------
(a) Native gamecore is likely faster to first lobby/zone-in, IF the server accepts stubbing service-only
    features (friend list, the service's mail, KB/FAQ search, presence profile files):
    - FFXi.dll uses 6 COM methods; FFXiMain needs no COM.
    - FFXiMain calls the table through its thunks, so on the Mac the host just provides a 1,560-
      entry pointer table. Every unimplemented slot can trap and log its caller, so the work can
      proceed one slot at a time.
    - The session path collapses to ~7 slots: 818/705 return 0/1; 221/222 resolve a host name;
      195/196 return handle/"done"; 1003 returns V (issued by our own sign-in); 936 returns the
      0x34-byte block. Per the LSB integration notes s6, LSB does not verify authCode, so any
      bytes may do (unverified). Alternatively, lift 0x1001a2d0 from a recompile of just that
      function.
    - Real cost: return conventions for the ~20-40 slots actually hit on boot->lobby->zone, and the
      path/file slots (126/127/284-287/908/910/1171) that read the viewer's install files.
(b) Recompiling gamecore is mechanically ~1/8 of FFXiMain, but it brings: a VS2005 CRT/SEH profile
    the recompiler has not handled, ATL/registry emulation, sockets+threads, and the sign-in
    problem of s6 (the account server on the wire, plus either the unmapped +0xcbc flow or credential
    poking). It wins only if full online-service feature fidelity inside FFXI is wanted.
A hybrid is worth considering: native gamecore, with pure-computation helpers (0x1001a2d0, MD5,
sprintf) taken from a partial recompile.
