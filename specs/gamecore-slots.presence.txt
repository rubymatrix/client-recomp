gamecore common-function-table slots: presence client, lists, text, KB search, misc
=====================================================================================
Date: 2026-09-24. Static only (capstone 5 + pefile over reverse-engineering/unpacked/*.unpacked.dll,
image base 0x10000000), plus the live call log gamecore_live_calls.txt (retail gamecore, signed in to
a private account server; the translated FFXiMain is rebased by -0x04500000 in that log, so an
argument 0x0bbf28c0 is FFXiMain 0x100f28c0). Scratch scripts: session scratchpad pp/*.py.
Confidence tags: HIGH = read directly from code; MED = read, but a detail rests on inference;
LOW = educated guess.

===================================================================================================
0. CONVENTIONS THAT HOLD FOR EVERY SLOT IN THIS GROUP                             confidence: HIGH
===================================================================================================
* CALLING CONVENTION: every slot target in this group ends in a plain `ret` (checked by recursive
  descent of each target: no `ret N`), and every FFXiMain call site cleans up itself
  (`add esp,4*N` / `pop ecx`) or reaches the slot by a tail-`jmp` from a 1-line cdecl wrapper.
  => ALL slots below are __cdecl: the callee pops NOTHING. "a0,a1,.." = dwords at [esp+4],[esp+8],..
     on entry. Return in eax (slot 283 returns a 64-bit value in edx:eax; slot 207 a 16-bit value
     in ax, FFXiMain masks with `and eax,0xffff`).
* FFXiMain reaches the table only through thunks (mov eax,[0x10456a6c]; jmp [eax+disp]). Most
  presence slots are wrapped again by 1-line functions at 0x100f1590..0x100f1a60.
* gamecore error codes are negative: 0xffffe3xx (-72xx) bad index/state; 0xfffff7fa (-2054) bad
  request handle; 0xffffebf0 (-5136) handle not in use; 0xfffffdfd (-515) not signed in to the
  online session (global 0x100aa8c8==0); 0xfffffefc (-260) request older than 100 s; 0xffffff00 (-256) no free
  request context; 0xffffec00 (-5120) bad argument; 0xffffd800 (-10240) bad file channel.
* FFXiMain reports negative codes from several service paths through 100182f0(err) -> 10018320 ->
  10018190 (the game's service-error reporter). Native stubs should therefore prefer "0 / empty
  record / done" over negative returns, except where noted.

presence ASYNC REQUEST MODEL                                                        confidence: HIGH
  Pairs: 165/166, 175/176, 179/180, 181/182 (poll also 180 in one state), 208/209, 273/274, 275/276,
  278/279, 280/281, 301/302 (and 195/196, not in this group).
  - START: takes one of 4 request contexts (0x338 bytes each at 0x10404ad0..0x104057b0; finder
    0x1001eba0), initialises it (0x1001ea00, 0x1001ff20), returns the context index 0..3 as the
    HANDLE, or 0xffffff00 if none is free. Start does no network I/O.
  - POLL(h): validator 0x1001ebd0: h<0||h>=4 -> -2054; ctx free -> -5136; not signed in
    (0x100aa8c8==0) -> frees ctx, -515; older than 100000 ms -> frees ctx, -260. Otherwise steps
    the request: 0 = BUSY, >0 (1) = DONE (ctx freed), <0 = FAILED (ctx freed).
  - FREE(h): slots 199 and 277 (both -> 0x1001fc30) cancel/free a context.
  - FFXiMain always:  h = start(); h<0 -> error;  then per frame r = poll(h): r==0 stay,
    r>0 advance, r<0 -> error path (network-mode failure, or service job failure + error report).
  => NATIVE GENERIC RULE: start returns 0 (a fake handle, never negative); poll returns 1 (DONE) on
     the first call; free returns 0. Retail "not signed in" (poll -> -515) would drive FFXiMain
     into its error paths, which is exactly what we do not want. Where DONE is followed by FFXiMain
     reading output written by the slot, the per-slot block says what to write.

FFXiMain "SERVICE JOB" STEP PROTOCOL (0x100f2c90 runner, step tables at 0x103620d0..0x10362330)
                                                                                  confidence: HIGH
  A service job is a NULL-terminated list of step functions step(job, phase). phase 0 = query,
  1 = begin, 2 = poll, 3 = cancel. Step return: 0x16 = busy (call again next frame), 0x17 = step done
  (advance), 0x18 = "item available" (iterator), 6 = cancelled, anything else = job failed with that
  code (if job+8 < 0 the runner calls 100182f0(job+8) = service-error report, then the requester's
  callback gets the code). Every step starts with 0x100f4570 (common init).
  Jobs are created by: 0x100f1f10 (auto, only if slot 836 returns 1) and the service UI in FFXiMain
  (0x101ff3f0..0x10201650: the service's mail / friend UI, via
  0x100f7000..0x100f76c0 C-API wrappers).

1a. Network-mode dispatcher 0x100da760 (mode in [obj+0x88], obj = [0x103601cc]).  conf: HIGH
  Per frame, from 0x100daf40 (which also calls slot 705). Modes are requested by 0x1023b540 via
  0x1023bb50 (mode) -> 0x100db180. On a handler returning -1 the dispatcher switches to mode 0xcb
  (error / disconnect dialog). Relevant handlers:
    mode 1   0x100ed7f0  lobby connect (818, 221/222, 195/196, 936, 1003; other group)
    mode 3   0x100ee170  ENTER WORLD with the selected character (uses 177, 183/184, 179/180,
                         181/180, 195/196). Always used by 1023b540 op 1 = "play character".
    mode 19  0x100ee0b0  175/176 (only when 1023b540's first argument is non-zero; not seen live)
    mode 17  0x100eeea0  181/182 then 179/180;  mode 18 0x100eef90 181/182.
                         Both requested only by 0x1023bc00, which has NO callers (dead).
  mode 3 (0x100ee170) in detail. States 0..9 are lobby traffic, 10..13 print messages, then:
    14  idx = 0x100efdb0(sel) -> 0x100efe00(contentId, worldWord, charIdPacked): scans slot 177
        records 0..63 for one with  (b[0]&1) && w[2]==1 && d[8]==contentId && d[0xc]==0 &&
        d[4]==packed.  None -> -1 -> mode fails -> error dialog.  Found: 177(idx,&rec):
          rec.q[0x10] bit 15 set   -> 195(chan=(q[0x10]>>16)&0x3f, idx, 0, -2, -1, 1); state 15
          bit 15 clear, state<20   -> state 16
    15  poll 196: 0 wait, >0 -> state 22 -> return 1 (mode done), <0 -> fail
    16  ebx=0x100efdb0(sel), edi=0x100efd30() (first 173 record with bit0 set and a free byte in
        rec+0x20..0x27, else -1 -> fail); 184(ebx,edi); 183(ebx,edi) <0 -> fail; h=179() -> 17
    17  poll 180(h): 0 wait, >0 -> 18, <0 fail;   18  h=181() -> 19;   19 poll 180(h) -> 20
    20  = state 14 again, but now "bit 15 clear" -> fail.
  The live log shows exactly states 14 -> 15 -> 22 (177 at 100efe2e for idx 0,1,2, then 177(2)
  at 100ee363, 195(0,2,0,-2,-1,1), 196 polled 15x until 1).
  FFXiMain values: character table at [[0x104df7b0]+0x13820 + i*0x8c], selected index at
  [[0x104df7b0]+0x1381c]; per entry: dword +4 = contentId, word +8 and byte +0xf = 24-bit
  character id, word +0xa = world word. 0x100efe00's packed id =
      (charId & 0xffff) | ((worldWord & 0xffff) << 16) | ((charId>>16 & 0xff) << 24)
  (the world word and the char-id high byte overlap in bits 24..31; world word is expected <256).
  => "NOT CONNECTED" CANNOT MEAN "NO 177 RECORDS". Native slot 177 must return, for the selected
     character, a record that 0x100efe00 matches, with bit 15 of q[0x10] set and handle index 0 in
     bits 16..21, so mode 3 goes 14 -> 195/196 -> done and never reaches 183/184/179/180/181.
     Source the values from the server's own lobby data or read them from FFXiMain's table above.

1c. FFXiMain service client object 0x104df8e8 (pointer 0x104df948)                    conf: HIGH
  0x100f76c0 creates it (from 0x100f0140 init and 0x10017710); 0x100f7710 -> 0x100f1d30 pumps its
  job queue once per frame (from 0x10103930, called by 0x100da760 every frame); 0x100f76e0 tears it
  down. 0x100f7750 (called by the lobby machine 0x100ed7f0) and 0x100f7770 call 0x100f1f10(1):
      if (word obj+4 == 0 && slot836() == 1) { obj+4 = 1; allocate job slots; friend-list scan
          (100e6b20/100e6c50/100e63d0: slots 167/169); queue the mail-folder jobs (100f2600,
          100f26a0, 100f2730: slots 126, 931/930/923, 291, 167/169/173, 278/279/282/288) }
  obj+4 also gates registering the service notification callback (0x100f1d10 -> 288(0x100f28c0)).
  The mail counters read by the in-game mail icon UI (0x100f6ee0.., 0x102007xx..0x102015xx)
  stay 0 unless jobs run.
  => "NOT CONNECTED" = slot 836 returns 0. Then no service job is ever started automatically, the
     per-frame pump finds an empty queue, and the mail icon shows nothing. UI-started jobs can
     still run; with the stubs below they finish immediately with empty results.
  (Retail returns 1 from 836 when the online session is NOT initialised, and a fetch-and-clear
  flag otherwise; live it returned 1. Returning 1 natively is also safe with the stubs below, just more code runs.)

      k = b - 0xa1;                         // JP mode
      if (k < 0x3f) {                       // half-width katakana 0xa1..0xdf -> full-width SJIS
        count++; kind = 2;
        if (i < len) { m = (u8)(src[i] + 0x22); if (m < 3) kind = m; }   // next 0xde / 0xdf
        w = TBL[kind][k];                   // u16, TBL[0]=0x10076644 (dakuten), TBL[1]=0x100765c4
        if (w != TBL[2][k]) { i++; count++; }  // (handakuten), TBL[2]=0x10076544 (plain)
        dst[o++] = w & 0xff; dst[o++] = w >> 8;     // stored so bytes come out as SJIS lead,trail
        continue;
      }
      if (i == len) break;                  // SJIS lead byte without trail: dropped
      dst[o++] = b; b = src[i++]; if (b == 0) break; dst[o++] = b;   // copy the 2-byte pair
    }
    dst[o] = 0; return count;
  The three 63-entry u16 tables are in gamecore .data at the addresses above (copy them verbatim;
  e.g. plain[0] = 0x4281 -> bytes 81 42).

  Native: implement exactly as above with LATIN = 1 (0 for a Japanese client). Return count.
