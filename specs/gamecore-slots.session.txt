gamecore common-function-table slots: session, lobby, per-frame pump, FFXi.dll's own slots
============================================================================================
Date: 2026-09-24. Static only (capstone 5 + pefile over reverse-engineering/unpacked/*.unpacked.dll,
image base 0x10000000), plus the live call log gamecore_live_calls.txt (translated FFXiMain against
retail gamecore). Table at gamecore 0x1006fbe8; slot N at +4*N. Scratch scripts (not in repo):
session scratchpad d.py / callers.py / grepm.py / gref.py.

CONVENTIONS THAT APPLY TO EVERY SLOT BELOW
  * Every slot in this group is CDECL: each gamecore target ends in a plain `ret` (no `ret N`), and
    every FFXiMain/FFXi caller cleans the stack (`add esp,4*n`) after calling the thunk
    (`mov eax,[tbl]; jmp [eax+disp]`). Pop count = 0 for all. A native slot reads its args at
    guest [esp+4], [esp+8], ... and leaves esp alone. Return value in eax.
  * "Handle" values are small non-negative ints; negative returns are error codes (retail uses
    them as -(code), several shown below). FFXiMain generally treats <0 as fatal for the step.
  * +0x5e0 (slot 376) holds the SAME pointer as +0x30c (slot 195): 0x1001db60. It is an alias in
    the table, not a second use: FFXiMain has no call to the +0x5e0 thunk. The live log labels
    195 as "+0x30c/0x5e0" because it resolves by address. Likewise +0x5e4 (377) = 0x1001db90, the
    engine 196 calls. Native: put the same function in both slots (harmless) or leave 376/377 null.

Confidence scale: HIGH = read instruction by instruction and matches the live log; MEDIUM = read
but a detail (meaning of a field, exact retail value) is inferred; LOW = inferred.

Convention: cdecl, no args (live: stack words are caller garbage). int pump(void).

  else: takes mutex 0 (0x10047fb0/fe0: WaitForSingleObject/ReleaseMutex on 0x103df808[0]), runs the

============================================================================================
C. THE cmd 4 sub 5 EXCHANGE AS gamecore PERFORMS IT (for a host that does it itself)
============================================================================================
Account-server implementation: its presence handler session_login() (dispatched from handle()),
with framing in that module's header comments and session() (hello/cipher selection).
Transport: TCP to the numbered presence host (fmt 0x10075430), port 51220 (a fresh connection per request; closed after the reply).
 1. Hello: client sends 0x28 bytes plaintext (byte 1 == 1 asks for plaintext, else encrypted);
    server replies 0x14 zero bytes + u32 nonce (plaintext). Client keeps the nonce (conn+0xb8).
 2. Encryption: OFB Blowfish with the sqIrc session key/IV of this member's sqIrc (P-IRC 51240)
    sign-in, re-seeded at the IV per message (gamecore copies the sqIrc cipher template,
    0x1001a170/0x1001a1a0). The account server identifies the member by which sqIrc key decrypts the
    first header. => an sqIrc sign-in must exist first.
 3. Request header 0x28: +0 u8 2, +1 u8 cmd=4, +2 u8 sub=5, +3 0, +4 u32 body len = 0x28,
    +8 16 zero bytes, +0x18 MD5(8 bytes from 0x1001a050(0x10404a88,0x10404a8c) ||
    0x10404a94[0..15] || nonce). The account server does not verify the MD5.
 4. Request body 0x28 (built by 195, 0x1001d7e0):
      +0x00..+0x0f  0 (u8,u8,u16,u32,u32,u32 all zero)
      +0x10 u8  handle (a1; 0 if handle < 0)
      +0x11 u8  1 if chr found in the handle's character table (0x10405820), else 0
      +0x12 u8  its index 0..7 (0 if not found)
      +0x13 u8  mode==0 ? 1 : 0          (account server: "login mode")
      +0x14 u16 contents class (a6; 1 = FFXI)
      +0x16 u8  openstat+1 (0 if handle < 0)
      +0x17 u8  friendauth != 0
      +0x18 u8  "changed" flag (0 on the first call ever)
      +0x19 u8  1
      +0x1a u16 0, +0x1c u32 0, +0x20..+0x27 not written by 195 (connection buffer residue; zero
              on a fresh slot - MEDIUM)
    The account server reads +0x10..+0x17 as the 8-byte ChangeMyStatus block.
 5. Reply header 0x18: +1 status (non-zero -> client error 5200+status), +4 body len,
    +8 redirect IP (must be 0).
 6. Reply body 0x20 = 0x1c bytes + sum32 checksum (client verifies). body[0..16) = V.
    Account server: V = ffxi_session_value(account_id) (one per sign-in serial; reused on the 2nd
    call), written to ffxi_sessions.password and to the account table's session_value in xidb
    (xidb.py publish_session_value). Remaining 0x0c bytes zero.
gamecore then derives the 0x34-byte block from (body, session IV, 64-bit value from 0x1001a1a0(0),
byte 0x10404a92) in 0x1001a2d0 (1,550 insns, pure computation) + 0x100135f0. Not needed: no server
checks it.

============================================================================================
E. DESIGN DECISIONS NEEDED
============================================================================================
D1. Source of V (and the whole 195/196 pair). Options:
  (a) Host-side presence: the host (a sign-in client, which could carry a C++ sqIrc+presence
      online session per docs/client.md) sends cmd 4 sub 5 itself when 195 is called, using the
      member's live sqIrc cipher, and 196 reports completion; V = reply body[0..16).
      Retail-accurate, gives friends correct FFXI presence (status block), no account-server change.
      Needs the host's sqIrc sign-in to be up before FFXI starts.
  (b) Pre-fetch: the host does one cmd 4 sub 5 with class 1 at sign-in, caches V, and native
      195/196 complete immediately (196 returns 1 on first poll); later status changes are
      forwarded asynchronously or dropped. Same server, fewer moving parts in the game thread;
      presence is less exact.
  (c) No presence: a private endpoint (e.g. an authenticated HTTP/RPC call to the account server)
      that runs ffxi_session_value + publish_session_value and returns V. Simplest for the Mac host,
      but a new server entry point that must authenticate the member some other way, and FFXI
      presence would not be announced.
  Recommendation: (a) if client/ has presence anyway; (b) as the first milestone. Either way the
  account server must be the issuer, because it is the only writer of the account table's
  session_value that LSB reads.
D2. Lobby address for 221/222: hard-map the lobby host name to a configured IP (recommended), or
  resolve it with the host's DNS/hosts file (retail behaviour; needs the redirect the Windows
  path solves with its host-redirect plugin).
D3. authCode block (936): zeros vs random. No server checks it; zeros are deterministic and fine.
D4. Slot 838 at shutdown: return 3 (quiet exit, recommended) or reflect the host's real online-session state.
D5. Slot 460 value (param block +0x44): 0xffffffff (no Viewer) unless the Viewer-replacement flow
  should set it; its meaning is not established.
